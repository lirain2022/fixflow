# RE:FIX 會員服務與零件需求設計

狀態：待使用者確認；本文件不是已完成的功能。

## 目的與已確認方向

一般會員登入後使用與首頁一致的服務網站，不進入內部維修工作介面。會員可以查看自己的報修狀態，並提出想更換或加裝的零件。依使用者對建議方案的同意，第一版採自由填寫零件需求，由管理員回覆，不做零件商城。

目前會員與管理員登入後共用 SystemApp；工單服務允許可見工單的使用者執行多項內部操作。因此這次包含後端授權調整，不能只隱藏選單。

## 入口與畫面

- 首頁保留 RE:FIX 導覽；會員登入頁與會員中心使用深色背景、冰藍色重點、圓角卡片，動態效果尊重減少動態偏好。
- 一般登入完成回首頁，右上角改為會員姓名、「會員中心」與登出。首頁不顯示私人工單明細。
- 會員中心位於 `/member.html`，包含「我的報修」、「零件需求」、「帳號設定」；不出現派工、全站設備或帳號管理。
- 從報修表單登入，接續原本表單確認；從進度查詢登入，直接開啟自己的工單列表。
- 管理員維持 `/system.html?portal=admin`。舊會員 `/system.html` 入口轉至會員區，保留已支援的 action 與 view 意圖，不接受任意外部轉址。
- 會員與管理員登入狀態仍分開。既有帳號與歷史工單保留，無須重新註冊。

## 會員中心與工單

首頁摘要顯示自己的處理中、待驗收及已結案數量，點選可篩選工單。列表有分頁、空白提示、錯誤重試與新增報修入口。

會員工單詳細頁顯示狀態、問題描述、位置、公開維修紀錄、已登錄費用、照片與留言。會員可對自己的未結束工單補充留言、上傳照片；在待派工／已派工時取消，在待驗收時確認結案或填原因退回維修。會員不能自行派工、開始維修、填維修紀錄或改費用。

尚未登錄費用顯示「尚未登錄」，不當成零元。維修中的內部費用草稿不傳給會員。第一版不增加正式報價同意或付款流程；「待我確認」僅呈現已存在的待驗收事項。

## 零件需求

從自己的工單提出需求；沒有工單時先報修，不建立無所屬的購物車。

欄位：零件名稱（必填，最多 120 字）、數量（1–99 整數）、用途／規格說明（必填，最多 2000 字）、參考連結（選填，最多 1000 字，只接受 HTTP/HTTPS）。連結只供點擊參考，伺服器不抓取網址內容。

需求以獨立資料紀錄保存，關聯工單與提出者，含建立／更新時間、狀態、管理員回覆及版本號。狀態為「待確認」、「已回覆」、「不適用」、「已撤回」。它不是實際維修零件，不加入人工費、零件費或總額。

- 會員可在待派工、已派工、維修中提出需求；待驗收、結案或取消後不接受新需求。
- 尚待確認的需求可由提出者撤回；要更改內容則撤回後重新提出，保留歷程。
- 管理員在現有工單詳細資訊內查看需求，回覆相容性、處理方式與需進一步確認的資訊；回覆不可空白。金額若在文字回覆中提及，仍不視為已收費。
- 需求回覆與撤回採版本檢查，避免同時操作覆蓋。送出時停用按鈕；送出結果不明時先重新載入確認，避免盲目重送。
- 管理員回覆會通知提出者；新需求通知管理員。會員可查看自己需求的狀態與歷史內容。

## 授權與相容性

依這次會員／內部系統分離的方向，取消一般會員原有的內部派工與費用操作能力；管理員保留現有完整維修流程。第一版不新增技師登入或變更帳號角色。

會員資料查詢由伺服器強制限制為本人建立的工單，無法藉由傳入其他工單 ID、篩選條件、附件 ID 或零件需求 ID 存取別人資料。管理端 API 必須驗證管理員角色，既有一般登入 API 不得繞過。既有非管理員帳號在本版使用會員服務。

新增 `/api/member` 服務介面，回應只包含會員需要的欄位。針對既有工單、派工、設備、費用、匯出、人員與通知等端點逐項驗證授權；會員功能移至會員端點後，不再以舊內部端點取得管理資料。

帳號設定沿用改密碼機制。登出清除會員登入狀態，私人資料不以公開快取保留。管理員與會員 API 皆保留停用帳號、密碼變更後工作階段失效的檢查。

## 驗證與交付

測試涵蓋登入導向、報修資料銜接、手機及鍵盤操作、只看本人資料、跨帳號工單／附件／需求存取拒絕、會員無法呼叫內部修改 API、管理員正常派工維修、需求提交／回覆／撤回／版本衝突、需求不計入費用。

資料表採新增方式，不刪既有工單或費用資料。先在隔離測試資料庫驗證，再以原專案副本檢查相容性；本機套用與 GitHub 推送分開交付，不把測試資料帶入正式資料庫。

## 方案取捨

建議獨立會員畫面搭配受限的會員 API：可清楚區分使用者服務與內部操作，並有伺服器端保障。僅修改現有工作區樣式仍容易留下管理操作入口；完整零件商城則需要庫存、價格、付款與訂單流程，超出本次已同意範圍。
