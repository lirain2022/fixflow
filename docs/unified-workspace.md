# FixFlow 統一工作台

## 目標與範圍

將既有報修、派工、維修與管理功能整合成一個可協作的工作台。同一網站、同一份工單資料，各人以自己的帳號登入並保留操作身分。
依本輪對話先採統一工作台方向；多重角色、設備、庫存及維修排程尚未確認，不視為已授權的新增模組。

## 既有功能盤點

目前已有三種角色、工單列表/搜尋/新增/編輯/取消、詳細視窗、派工、維修紀錄、照片、留言、歷程、管理員統計與帳號新增/停用。
目前缺少共同首頁、可點擊的待辦入口，以及同時呈現待派工單與技師工作量的派工中心。各角色依現在權限使用同一資料來源。

## 第一批整合

1. 工作首頁：所有角色登入後先看到自己的可見工單統計。卡片可帶條件跳至工單中心；報修者待確認、技師待處理/維修中、管理員待派工/逾期。
2. 工單中心：保留原流程，提供清楚的狀態入口與既有搜尋；技師仍只看被指派工單，報修者只看自己工單。
3. 派工中心：管理員同時查看待派工清單、啟用技師及已派工/維修中/逾期件數。選擇工單與技師後確認派工，成功後刷新工作量；並行操作衝突顯示後端錯誤。
4. 技師工作台：首頁待辦直接進入對應列表，仍由被指派技師開始維修與提交紀錄。
5. 人員與統計：保留管理員帳號管理，技師工作量由資料庫實時計算；不將工單件數標示為線上狀態或排班可用性。
6. 工單詳細：所有角色看同一工單的照片/留言/維修與歷程，操作按鈕依角色顯示，後端仍為授權依據。

## 資料與接口

- 不變更既有帳號角色、不合併他人身分、不搬移工單資料。
- 新增 GET /api/workspace/summary：依登入人員可見範圍統計狀態、逾期；不使用管理員共享快取。
- 新增 GET /api/workspace/technicians：僅管理員可讀啟用技師工作量，不回傳密碼或 JWT。
- 既有 GET /api/tickets 與 PATCH /api/tickets/{id}/assign 繼續作為查詢與派工接口。
- 工單列表新增 overdue 可選篩選，與統計沿用相同逾期定義。
- 前端將首頁/派工中心拆成獨立元件；保留現有詳細與表單，避免複製業務規則。

## 驗收

- 客戶與技師的首頁計數不可包含他人的資料。
- 客戶/技師不能透過 API 存取人員工作量。
- 卡片跳轉條件與列表相符；搜尋與頁碼在更換視圖時重設。
- 管理員派工後，待派數減少、技師負載增加，技師登入看得到工作。
- 既有註冊、報修、維修、結案、圖片、留言與帳號停用測試保持通過。
- 手機可完成首頁導覽與派工；錯誤和載入狀態清楚可見。

## 執行順序

先測試後端可見範圍和工作量，再新增接口；接著首頁與派工元件、導覽整合，最後用三種角色執行瀏覽器驗收並更新操作教學。
